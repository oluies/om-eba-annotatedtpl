# The Quarto spike

One `.qmd`, rendered twice: HTML for a public site and GitHub-flavoured markdown for a
catalogue that takes markdown and nothing else. The question was whether one source can
serve both without a second pipeline, and whether a page whose numbers come out of the
DPM database at build time is better than a page whose numbers were typed in.

```bash
uv sync --group docs           # ipykernel, nbclient, nbformat - not installed by `uv sync`
./render.sh                    # F_18.00.a and K_47.00.a, both formats
./render.sh C_01.00            # any templates you name
./render.sh --framework DORA   # a whole framework, with an index page linking them
DPM2_DB=../source/dpm2/dpm2_4_3.duckdb ./render.sh    # the same pages under 4.3
```

And into the catalogue, which is the second destination this exists for:

```bash
uv run import_to_openmetadata.py --quarto quarto/_md --under FINREP --dry-run
uv run import_to_openmetadata.py --quarto quarto/_md --under FINREP   # writes them
```

`_site/` is the site, `_md/` is what an OpenMetadata article would be given. Neither is
committed, and nor are the per-template `.qmd` files: all three are generated from the
database, which is the point.

## What it answered

**One source, two destinations: yes.** `_md/F_18.00.a.md` is 5.9 kB of plain markdown -
headings, prose, pipe tables - with no HTML in it and nothing to post-process. It would
go into `PUT /v1/contextCenter/pages` as it stands. The HTML is a Quarto website with
search and a table of contents, and the two were produced from the same file by changing
`--to`.

**Numbers computed rather than copied: yes, and it changes what the page can say.** The
sentence "1,014 reportable cells, 15 dimensions, 498 validation rules reaching it, 8 of
them switched off" is four queries. Under 4.3 it is a different sentence, because
`render.sh` was pointed at a different database and nothing else changed.

**Parameters are the wrong mechanism.** Quarto takes `-P`, but with the Python engine it
routes through papermill, which renders a copy of the file under a temporary name. The
page title becomes `quarto-inputa2d3288ac1e1f384`, the output is `template.html` whatever
template it holds, and the search index gets one entry called "template". A four-line
generated stub per template - title, the template code, `{{< include _body.qmd >}}` -
costs nothing and gives Quarto what it is built around: a file per page, named after the
page. `pages.py` writes them; papermill is not a dependency.

**The queries do not belong in the page.** They are in `_dpm.py` as ordinary functions,
so ruff and ty see them and the tests could. A 20-line join inside a notebook cell is a
join nobody reviews.

## What it found in the data, while being written

The spike is a vehicle, but two of the page's own claims were wrong before they were
measured, which is an argument for computing them:

- A first version of the history section reported that **479 of 479** datapoints in
  `K_47.00.a` had moved, which is the kind of number that is obviously an error in the
  query rather than a fact about the world. It conflated *this datapoint has sat at
  another row or column* with *this datapoint is also reported by another template*. The
  `.a`/`.b`/`.c` variants of a template share datapoints by design. Split apart:
  `F_18.00.a` has 56 moved and 172 shared, `K_47.00.a` has 47 moved and 479 shared.
- `K_47.00.a` row `0010` was reworded in DPM 4.1, from `1. Loans and advances…` to
  `0.1 Loans and advances…`. The coordinate did not move and the datapoint did not
  change; the sentence a reader is shown did. That is the history of a description, and
  it is readable only by diffing `HeaderVersion` - the `ChangeLog` table is present and
  empty in every release the EBA ships.

## Why Quarto rather than the alternatives

The deciding constraint is the second destination. OpenMetadata takes markdown; it has no
user-defined widget and no way to host a page of ours. So the question is not "which
static site generator is nicest" but "which one emits a publishable site *and* clean
markdown from one source".

- **[Evidence](https://evidence.dev)** - markdown with SQL blocks against DuckDB,
  building a static site with DuckDB-WASM in the browser. The closest fit for a public
  data tool, and the one to reach for if the site were the only destination. It emits a
  site, not markdown, so the catalogue would need a second pipeline.
- **[Observable Framework](https://observablehq.com/framework)** - data loaders at build,
  DuckDB-WASM at runtime, the strongest interactive story of the three. Same objection,
  and it would overlap the Scala.js page that already does exactly this.
- **MkDocs Material / Docusaurus** - good navigation and search, no executable cells, so
  every number would be generated by a separate script and pasted in. That is what the
  pack already does with `gen_pack.py`; adding one of these would buy navigation only.
- **Quarto** - multiple output formats from one source is the feature the others do not
  have, and the Python engine means the numbers are queries. Worth knowing:
  [Quarto 2 is a Rust rewrite announced for late 2026](https://en.wikipedia.org/wiki/Quarto_(software)),
  backward compatible with Quarto 1 files, so nothing written here is a bet against it.

What none of them replaces is the interactive page: Quarto renders once, at build, and a
reader who wants to ask their own question needs the query to run in their browser. The
two are complements, which is why the navbar links to it.

## A whole framework

`./render.sh --framework FINREP` writes a page per template and an index that links them,
and `.github/workflows/wasm-data.yml` publishes that under `/templates/` on the same site
as the query page. The workflow renders from a release you name rather than from the
newest, because the newest is 4.4 and 4.4 is a draft: a page that reads like settled
documentation should not be generated from one without someone saying so.

Three things that only showed up at 150 pages rather than at two:

- **A title is not a safe YAML scalar.** F_40.02 is `Scope of the group:
  "instrument-by-instrument"`, which has both the colon and the quotes that end a title
  early, and Quarto's answer is a YAMLException and no pages at all - not a bad page.
  `json.dumps` produces a scalar YAML reads correctly, since YAML 1.2 takes a JSON string.
- **`sum()` over no rows is NULL.** A template whose datapoints are placed nowhere else
  rendered `**{None:,} have sat at another row or column**`, which fails the build with a
  TypeError two hundred pages in. `coalesce(..., 0)` in the query, not a guard in the page.
- **Quarto clears the output directory per render, not per format.** The second project
  render took the first one's HTML with it, and the count at the end of `render.sh` is
  what noticed. `--no-clean` on the second.

## Into OpenMetadata

`import_to_openmetadata.py --quarto quarto/_md --under FINREP` imports the rendered
markdown as Context Center pages: one section named after the framework, whose body is
the framework index, with a page per template under it. It reuses everything the pack's
own import already does - the preflight that tells an API root from an ingress, the check
that the body actually landed, the reindex - because the files are markdown either way.

`split_title` already did the one Quarto-specific thing needed: OpenMetadata renders the
page's displayName as a heading, so a body starting with the same `# F_18.00.a - ...`
shows the title twice. It takes the H1 for the displayName and drops it from the body.

Not verified against a live server. Everything above the HTTP call is exercised by
`--dry-run`, which prints the tree it would write; what no amount of local work can
answer is whether that server accepts a 6 kB body with pipe tables in it.

## What it costs

- A dependency group (`docs`: ipykernel, nbclient, nbformat) that `uv sync` does not
  install, so the pack, the tools and the tests are untouched by it.
- About 4 seconds a page on this machine, most of it kernel startup. A full build of
  1 174 templates would want `execute: freeze` or a single kernel, which Quarto supports.
- A second place where a description is composed. `_dpm.described()` is deliberately one
  function so that the page, the pack and the catalogue cannot drift apart - but it is a
  copy of the rule that `dpm_lookup.py` applies, and if this becomes more than a spike
  the two should be one.
